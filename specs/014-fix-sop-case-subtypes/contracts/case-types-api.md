# Contract: POST /api/dashboard/sop/case-types

**Feature**: 014-fix-sop-case-subtypes
**Endpoint**: `POST /api/dashboard/sop/case-types`
**Auth**: `iron-session` cookie (admin-scoped)
**Owner**: API package; consumer is the dashboard SOP editor.

## Purpose

The dashboard editor saves the firm's full case-types tree (case types +
their nested sub-types) via this single POST. The server diffs the
incoming list against the persisted state and applies inserts, updates,
and deletes atomically per request. This feature tightens the input
validation to enforce trimmed-non-empty labels, deterministic
slug-from-label derivation, and case-insensitive label uniqueness within
each parent.

## Existing Behavior (unchanged)

- Request body is the full ordered case-types list (not a delta).
- Identity is matched by `slug` for case types and by `slug` for
  sub-types within their parent.
- The diff applier processes deletes, updates, and inserts in that order.
- Returns `200 OK` with the updated tree on success; `400` with a Zod
  validation error on input failure; `500` on DB errors.

## Request Body Schema

```ts
{
  case_types: Array<{
    slug: string;            // ^[a-z][a-z0-9_]*$
    label: string;           // trimmed, non-empty, ≤ 80 chars
    position: number;        // integer ≥ 1
    is_in_scope: boolean;
    sub_types: Array<{
      slug: string;          // ^[a-z][a-z0-9_]*$
      label: string;         // trimmed, non-empty, ≤ 80 chars
      position: number;      // integer ≥ 1
    }>;
  }>;
}
```

### New Validation Rules (this feature)

| Rule | Scope | Layer | Error Code |
|------|-------|-------|------------|
| `label.trim().length > 0` | Each case type and each sub-type | Zod schema in route handler | `LABEL_EMPTY` |
| `label.trim().length <= 80` | Each case type and each sub-type | Zod schema | `LABEL_TOO_LONG` |
| `slug` must equal the deterministic derivation of `label` (lowercase ASCII-fold, non-`[a-z0-9]` → `_`, leading digits stripped) | New sub-types only (i.e., sub-types whose slug is not present in the persisted state for this parent) | `case-types-diff.ts` | `SLUG_MISMATCH` |
| Existing sub-types: `slug` must remain stable across the request — incoming slug must equal the persisted slug for the matched ID. | All sub-type updates | `case-types-diff.ts` | `SLUG_LOCKED` |
| Within each parent's `sub_types`, all `label.trim().toLocaleLowerCase('en-US')` values MUST be distinct. | Per parent | `case-types-diff.ts` | `LABEL_DUPLICATE` |
| Within `case_types`, all `slug` values MUST be distinct (existing rule). | Top level | `case-types-diff.ts` | `SLUG_DUPLICATE` |
| Within each parent's `sub_types`, all `slug` values MUST be distinct (existing rule). | Per parent | `case-types-diff.ts` | `SLUG_DUPLICATE` |

The `SLUG_MISMATCH` error fires only when the **client** authored a sub-type whose slug wasn't generated by the deterministic rule. The dashboard UI auto-derives the slug, so legitimate use of the editor never trips this; the rule defends against custom-client tampering and mistakes.

The `SLUG_LOCKED` error fires when an admin tries to "rename" a sub-type by changing its slug rather than its label. Renames must be label-only.

## Response

### Success (200)

```json
{
  "case_types": [
    {
      "id": "ct_abc",
      "slug": "dui",
      "label": "DUI",
      "position": 1,
      "is_in_scope": true,
      "sub_types": [
        { "id": "st_xyz", "slug": "first_offense", "label": "First Offense", "position": 1 }
      ]
    }
  ]
}
```

### Validation Error (400)

Returns the Zod issue list. New error codes are surfaced via Zod's
`refine`/`superRefine` `params.code` so the client can render targeted
messages:

```json
{
  "error": "validation_failed",
  "issues": [
    {
      "code": "custom",
      "path": ["case_types", 0, "sub_types", 2, "label"],
      "message": "Sub-type label \"First Offense\" already exists under \"DUI\".",
      "params": { "code": "LABEL_DUPLICATE" }
    }
  ]
}
```

### Atomicity Guarantee (FR-014)

The full payload either succeeds or fails as a unit. On any validation
failure or DB error, no partial mutation is applied. Implementation:
`diffCaseTypes` runs all the rule checks before issuing any DB write, and
the existing transactional pattern (sequential delete → update → insert)
runs inside a single Drizzle transaction. (The current implementation
issues these as separate statements; this feature wraps them in a
transaction if they aren't already.)

## Authorization (unchanged)

Request must carry a valid `iron-session` cookie identifying an admin
member of the account. Cross-account writes are blocked at the DB layer
by `case_types.account_id` checks already in place.

## Tests

- Unit tests on `case-types-diff.ts` covering each new rule (one
  test per error code) — extend `case-types-diff.test.ts`.
- Unit test on the route handler asserting the wire-format error shape
  for a `LABEL_DUPLICATE` rejection.
- Walk spec extension on `sop-tabs.walk.spec.ts`:
  1. Admin enters a label "First Offense" that collides with an existing
     sub-type → save button shows the inline error and no row is
     persisted (verify by reload).
  2. Admin enters a label "Second Offense" → slug auto-fills to
     `second_offense` (verify by reading the rendered slug span); save
     succeeds; reload shows the new row.
  3. Admin clears all sub-types under a case type → warning indicator
     appears in the case-type header row (verify with a `data-testid`).
