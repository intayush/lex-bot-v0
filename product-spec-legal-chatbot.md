# Product Specification: Legal Chatbot for Law Firm Client Intake & Lead Qualification

**Version:** 0.1 (MVP / Rapid Prototype)
**Date:** 2026-05-09

---

## 1. Overview & Objectives

### 1.1 Product Definition

An embeddable AI chatbot that handles client intake and lead qualification for law firms. Delivered as a JavaScript library that integrates directly into a lawyer's existing website.

### 1.2 Primary Value Proposition

Reduces response time from hours/days to seconds, increasing lead conversion. When a potential client visits a law firm's website with a question, the chatbot engages immediately — qualifying the lead, collecting relevant case information, and flagging urgent matters for attorney review.

### 1.3 Target User

Small-to-mid-size law firms with existing websites (static or server-rendered). Firms that want to capture more leads without hiring additional intake staff.

### 1.4 End User

Potential clients visiting a lawyer's website who have legal questions or are seeking representation. They expect immediate, relevant responses and a frictionless way to communicate their legal needs.

### 1.5 Core Problem

Lawyers lose leads because they cannot respond fast enough. Manual intake is slow and unscalable — a potential client who doesn't get a response within minutes will move to the next firm. Chatbots solve this by providing instant engagement, qualifying leads through structured questions, and collecting case data 24/7.

### 1.6 MVP Scope

This specification covers a rapid prototype targeting static website integration. The following are explicitly excluded from MVP: payment processing, CRM integrations, multi-tenant authentication, and advanced analytics.

### 1.7 Success Metric

A lawyer can install the widget, configure guardrails, run the crawler, and have a working chatbot handling intake questions on their website within 30 minutes.

### 1.8 Deployment Model

- **Context files:** Self-hosted on the lawyer's own server (markdown files generated by the crawler)
- **Chatbot API & Dashboard:** SaaS, hosted and managed centrally
- **Chat Widget:** Client-side JS library embedded in the lawyer's website

### 1.9 LLM Provider

The chatbot is powered by a pre-integrated Gemini model provided by us. Lawyers do not need to supply their own API keys or configure LLM settings — the model is ready to use out of the box. This reduces onboarding friction and ensures consistent chatbot quality across all deployments.

### 1.10 Compliance

Architecture respects attorney-client privilege through the following measures:

- **Context files** (website content, firm information) remain on the lawyer's own infrastructure.
- **Conversation data** (chat transcripts, extracted lead info) is stored on the SaaS server in the SQLite database. Lawyers explicitly consent to this during onboarding — the SaaS acts as a data processor, not data owner.
- **Data ownership:** The lawyer retains ownership of their conversation data and lead records. They can export or delete their visible data at any time via the dashboard.
- **Data retention:** A copy of all conversation data and lead records is retained on our servers indefinitely, even after the lawyer deletes their copy. This is disclosed in the terms of service and serves purposes including: service improvement, abuse prevention, compliance auditing, and dispute resolution.
- **Minimization:** Only data necessary for lead qualification is extracted and stored. The lawyer-facing view respects their deletion requests, while the backend retains a separate archived copy.

The system is designed so that the lawyer's website content never leaves their infrastructure, while operational data (conversations, leads) is stored on the SaaS with clear consent and ownership terms.

### 2.3 Context Flow

1. **Crawl phase (one-time or scheduled):** Crawler CLI runs against the lawyer's website → outputs structured markdown files → stored on the lawyer's server alongside their website.
2. **Query phase (real-time):** When a user asks a question, the API Server's agent fetches relevant markdown files from the lawyer's context store, assembles them into prompt context, and sends to the LLM.

### 2.4 Widget ↔ API Communication

- Streaming endpoint for real-time chat responses (Vercel AI SDK `useChat` compatible)
- REST endpoint for session initialization and lead submission
- Authenticated via site-specific API key issued through the dashboard

**API Key Authentication Flow:**

1. Lawyer generates an API key in the dashboard (format: `lc_live_` + 32-character random string via `nanoid`)
2. Key is stored as a bcrypt hash in SQLite (the plaintext is shown once at generation, never again)
3. Widget sends the key in the `x-api-key` header with every request
4. API server hashes the incoming key and looks it up in the `api_keys` table
5. If matched, the request is associated with that lawyer's account and configuration is loaded
6. If not matched, returns `401 Unauthorized`

This is a static key lookup — no JWT signing or token refresh is involved. The key identifies which lawyer's configuration and context store to use.

### 2.5 Dashboard ↔ API Communication

- Authenticated REST API for:
  - Configuration CRUD (guardrails form data)
  - Lead data reads (classified leads, chat transcripts)
  - Crawler status and context file management

### 2.6 SQLite as MVP Persistence

Stores:
- Lead records with classification (urgent/normal)
- Chat session history
- Configuration data (guardrail settings)
- Archived data (retained copies after user deletion)

SQLite is chosen for MVP simplicity. The schema is designed to be portable — migration to PostgreSQL requires only a connection string change, no schema redesign.

### 2.7 LLM Integration

The API server uses Vercel AI SDK with the `@ai-sdk/google` provider to connect to the pre-integrated Gemini model. The model configuration (model version, temperature, max tokens) is managed internally — lawyers do not interact with LLM settings.

```typescript
import { google } from '@ai-sdk/google';

const model = google('gemini-2.5-flash');
```

### 2.8 Agent Architecture

The chatbot operates as a tool-calling agent with access to:
- **Context search tool** — searches and retrieves relevant markdown files from the context store
- **Lead classification tool** — invokes the legal case analyzer to determine urgency
- **Intake question tool** — decides the next qualifying question based on conversation state

### 2.9 Configuration Injection

Guardrail data (from the lawyer's configuration form) is injected as system prompt context at the start of every conversation. This defines the chatbot's persona, scope boundaries, and response constraints without requiring model fine-tuning.

### 2.10 Stateless Widget, Stateful Server

The chat widget holds no sensitive state — it is a pure UI layer. All session state, conversation history, and lead data live server-side. This ensures:
- No sensitive data in the browser beyond the current visible conversation
- Sessions survive page refreshes
- The widget JS bundle remains lightweight

### 2.11 Separation of Concerns

- **Crawler CLI** — Standalone tool. Runs once during setup or on a schedule (e.g., via cron or CI). Has no runtime dependency on the API server.
- **API Server + Dashboard** — The only always-running services. Handle real-time chat, configuration management, and lead storage.
- **Context Store** — Passive file storage. Read-only at query time. Updated only when the crawler runs.

## 3. Component 1: Web Crawler / Context Builder

### 3.1 Purpose

A CLI tool that crawls a lawyer's website and outputs structured markdown files that serve as the chatbot's knowledge base. This is the primary mechanism for giving the chatbot relevant, firm-specific context.

### 3.2 Execution Model

- Runs locally on the lawyer's machine (or their developer's machine) or as a CI pipeline step
- Not a hosted service — no ongoing infrastructure cost for crawling
- Can be re-run on demand or scheduled via cron/CI to keep context fresh

### 3.3 CLI Interface

```bash
npx legal-chatbot-crawl --url https://example-lawfirm.com --output ./chatbot-context/
```

**Options:**

| Flag | Description | Default |
|------|-------------|---------|
| `--url` | Root URL to crawl (live website) | Required (unless `--input`) |
| `--input` | Local directory of HTML files (alternative to `--url` for dev/testing) | None |
| `--output` | Output directory for markdown files | `./chatbot-context/` |
| `--exclude` | Glob patterns for URLs to skip | None |
| `--max-pages` | Maximum pages to crawl | 100 |
| `--config` | Path to optional config file | `.crawlerrc.json` |

### 3.4 Input

- A single URL (the site root) as the crawl entry point
- Optional configuration file (`.crawlerrc.json`) for:
  - URL exclusion patterns (e.g., `/admin/*`, `/login`)
  - Custom selectors for content extraction
  - Max crawl depth

### 3.5 Rendering Strategy

#### Client-Side Rendering Support
Uses a headless browser (Playwright) to render JavaScript-heavy pages before extracting content. Handles SPAs, React-rendered pages, and dynamically loaded content.

#### Server-Side Rendering Support
Falls back to simple HTTP fetch + HTML parsing for static/SSR pages. Faster and less resource-intensive when JS execution is not required.

#### Auto-Detection
The crawler automatically detects whether a page requires JS rendering:
1. Fetches the page via HTTP first
2. If the HTML body is mostly empty or contains JS bootstrap markers (e.g., `<div id="root"></div>` with no children), re-fetches using Playwright
3. Otherwise, proceeds with the static HTML

### 3.6 Scope Restriction

- Only crawls pages within the same domain as the root URL
- Ignores external links, third-party resources, and subdomains
- Respects `robots.txt` directives
- Uses `sitemap.xml` (if available) as an additional source for page discovery

### 3.7 Link Discovery & Traversal

- Follows internal links (`<a href>`) to discover all reachable pages
- Parses `sitemap.xml` for additional URLs not linked in navigation
- Respects `max-pages` limit to prevent runaway crawls on large sites

### 3.8 Content Extraction

Strips non-content elements and extracts only meaningful page content:

**Extracted:**
- Headings (h1–h6)
- Paragraphs and body text
- Lists (ordered and unordered)
- Tables
- Structured data (practice areas, attorney bios, contact info)

**Stripped:**
- Navigation menus and headers
- Footers
- Sidebars and ads
- Cookie banners and modals
- Script and style tags

### 3.9 Deduplication

- Computes content hash for each page
- Detects duplicate/near-duplicate pages (e.g., paginated listings, print versions)
- Consolidates duplicates into a single markdown file with a note referencing alternate URLs

### 3.10 Output Structure

Output is organized into a `pages/` subdirectory with filenames derived from URL path. The `_manifest.json` sits at the root of the output directory:

```
chatbot-context/
├── _manifest.json
└── pages/
    ├── index.md
    ├── about.md
    ├── practice-areas--family-law.md
    ├── practice-areas--personal-injury.md
    ├── attorneys--john-smith.md
    ├── attorneys--jane-doe.md
    ├── faq.md
    └── contact.md
```

Path separators (`/`) are converted to double dashes (`--`). The `_manifest.json` file lists all crawled pages with metadata for the agent search layer. The `pages/` subdirectory keeps crawler output separate from configuration files that may be added later (see Section 5: Context Storage Structure).

### 3.11 Frontmatter Schema

Each markdown file includes YAML frontmatter:

```yaml
---
title: "Family Law Practice"
source_url: "https://example-lawfirm.com/practice-areas/family-law"
crawled_at: "2026-05-09T14:30:00Z"
word_count: 847
section_type: "practice-area"
content_hash: "a3f2b8c1..."
---
```

**`section_type` values:** `practice-area`, `attorney-bio`, `faq`, `blog-post`, `contact`, `about`, `general`

The crawler infers `section_type` from URL patterns and page content heuristics.

### 3.12 Incremental Crawling

On subsequent runs:
1. Reads existing `_manifest.json` from the output directory
2. Fetches pages and computes content hashes
3. Only overwrites markdown files whose content has changed
4. Adds new pages, removes files for pages that no longer exist
5. Updates `_manifest.json` with current state

This keeps crawl times short for routine updates and avoids unnecessary file churn.

## 4. Component 2: Lawyer Configuration Form

### 4.1 Purpose

A structured form that captures how the chatbot should behave, what topics it can and cannot discuss, and how it should represent the firm. This data serves as the primary guardrail mechanism — it defines the chatbot's persona, scope, and boundaries without requiring any prompt engineering knowledge from the lawyer.

### 4.2 Access Model

- Available within the SaaS dashboard as a dedicated configuration section
- Revisitable and editable at any time
- Changes take effect on the next conversation (existing active sessions are not interrupted)

### 4.3 Form Sections

#### Section A: Chatbot Persona

| Field | Type | Description |
|-------|------|-------------|
| Firm name | Text | Full legal name of the firm |
| Chatbot name | Text | Display name for the chatbot (e.g., "Sarah", "FirmAssist") |
| Greeting message | Textarea | Initial message shown when chat opens |
| Tone | Select | `formal` / `friendly` / `neutral` |
| Language | Select | Primary language for responses (default: English) |

#### Section B: Practice Area Scope

| Field | Type | Description |
|-------|------|-------------|
| Active practice areas | Multi-select checklist | Areas the chatbot should discuss (e.g., Personal Injury, Family Law, Criminal Defense, Estate Planning) |
| Custom practice areas | Text (repeatable) | For areas not in the default list |
| Out-of-scope response | Textarea | What the chatbot says when asked about areas not selected (default: "I'm not able to help with that area, but I can connect you with our team.") |

#### Section C: Qualifying Questions

| Field | Type | Description |
|-------|------|-------------|
| Intake questions | Ordered list (repeatable) | Questions the chatbot should ask to qualify a lead |
| Question order | Drag-and-drop | Priority order for asking questions |
| Required vs. optional | Toggle per question | Whether the chatbot must ask this or only if relevant |

**Default qualifying questions (pre-populated, editable):**
1. What type of legal matter do you need help with?
2. When did this issue first arise?
3. Have you spoken with another attorney about this matter?
4. What is your preferred method of contact?
5. What is your availability for a consultation?

#### Section D: Response Boundaries

| Field | Type | Description |
|-------|------|-------------|
| "Never say" rules | Text (repeatable) | Explicit prohibitions the chatbot must follow |

**Default rules (pre-populated, editable):**
- Never provide specific legal advice or legal opinions
- Never promise case outcomes or success rates
- Never discuss fee structures unless explicitly listed on the website
- Never disclose information about other clients
- Never recommend against seeking legal representation

#### Section E: Escalation Triggers

| Field | Type | Description |
|-------|------|-------------|
| Escalation conditions | Text (repeatable) | Conditions that trigger immediate human referral |
| Escalation message | Textarea | What the chatbot says when escalating |

**Default escalation conditions:**
- User mentions active danger to themselves or others
- User describes an emergency requiring immediate legal action
- User expresses frustration with the chatbot and asks for a human
- User's matter falls outside all configured practice areas

#### Section F: Contact Information

| Field | Type | Description |
|-------|------|-------------|
| Phone number | Text | Primary contact number |
| Email | Text | Intake email address |
| Office hours | Structured (day/time pairs) | When the firm is available |
| After-hours message | Textarea | What to say outside office hours |

#### Section G: Custom Instructions

| Field | Type | Description |
|-------|------|-------------|
| Additional instructions | Textarea (large) | Freeform field for any behavioral instructions not covered above |

### 4.4 Form Output Format

On save, the form data is:
1. Stored as structured JSON in the SQLite database (source of truth)
2. Converted to a markdown guardrails file (`_guardrails.md`) that gets deployed to the lawyer's context store

```json
{
  "version": 3,
  "saved_at": "2026-05-09T15:00:00Z",
  "persona": { "firm_name": "...", "chatbot_name": "...", ... },
  "practice_areas": { "active": [...], "out_of_scope_response": "..." },
  "qualifying_questions": [...],
  "boundaries": { "never_say": [...] },
  "escalation": { "triggers": [...], "message": "..." },
  "contact": { "phone": "...", "email": "...", ... },
  "custom_instructions": "..."
}
```

### 4.5 Versioning

- Each save creates a new version (auto-incrementing integer)
- Previous configurations are retained in the database
- The dashboard shows version history with timestamps and a diff view
- One-click rollback to any previous version

### 4.6 Preview Mode

After saving a new configuration:
1. A "Preview" button launches a sandboxed chat widget within the dashboard
2. The lawyer can test conversations against the new config
3. Preview sessions are not stored as real leads
4. Once satisfied, the lawyer clicks "Publish" to make the config live

### 4.7 Configuration Deployment Mechanism

When the lawyer clicks "Publish," the guardrails configuration is deployed through a two-path system:

**Primary path (runtime — automatic):**
The API server reads guardrails configuration directly from the SQLite database at conversation start. This is the authoritative source. No file transfer to the lawyer's server is needed for guardrails to take effect.

**Secondary path (context store sync — manual):**
A CLI command syncs the published configuration to the lawyer's context store as markdown files:

```bash
npx legal-chatbot-sync --api-key lc_live_xxxxx --output ./chatbot-context/
```

This generates `_guardrails.md` and `config/` files in the context store. This is useful for:
- Keeping a local copy of the configuration under version control
- Allowing the agent's context search to reference guardrails alongside page content
- Providing a human-readable audit trail on the lawyer's server

**In practice:** The API server always uses the database as the source of truth for guardrails. The context store files are supplementary — the chatbot works correctly even if the sync command has never been run.

## 5. Component 3: Context Storage Structure

### 5.1 Purpose

A unified directory structure that combines crawled website content and guardrail configuration into a single, searchable context layer. This is the chatbot's entire knowledge base — everything it knows about the firm comes from these files.

### 5.2 Location & Accessibility

Lives on the lawyer's server alongside their website files. The context store is a static directory served over HTTPS so the API server can fetch files at query time.

```
project-root/
├── public/              (website files)
├── src/                 (website source)
└── chatbot-context/     (context store)
```

**Accessibility requirement:** The `chatbot-context/` directory must be publicly accessible over HTTPS at a stable URL (e.g., `https://example-lawfirm.com/chatbot-context/`). The API server fetches files from this URL at query time — there is no authentication on the context store endpoint.

**Security note:** The context store contains only publicly available website content (already visible on the lawyer's site) and non-sensitive configuration. No private data, credentials, or client information should ever be placed in the context store. Sensitive guardrail configuration (e.g., internal notes in custom instructions) is stored in the SaaS database and injected via system prompt — it never appears in the public context store.

**Latency consideration:** The API server caches the `_manifest.json` and recently fetched markdown files in memory (TTL: 5 minutes). This means the API server does not make a network request to the lawyer's server on every chat message — only on cache misses or when context for a new topic is needed.

### 5.3 Directory Layout

```
chatbot-context/
├── _manifest.json                         # Index of all files
├── _guardrails.md                         # Generated from dashboard form
├── pages/                                 # Crawler output
│   ├── index.md
│   ├── about.md
│   ├── practice-areas--family-law.md
│   ├── practice-areas--personal-injury.md
│   ├── attorneys--john-smith.md
│   ├── attorneys--jane-doe.md
│   ├── faq.md
│   └── contact.md
```

### 5.6 Markdown as Universal Format

Both crawled content and configuration use markdown because:
- LLMs parse markdown natively with high fidelity
- No serialization/deserialization overhead at query time
- Human-readable and editable if a lawyer wants to manually adjust content
- Consistent format reduces prompt engineering complexity

### 5.7 File Size Constraints

- Individual markdown files are capped at approximately 2000 words
- Pages exceeding this limit are split into logical sections by heading (e.g., a long FAQ page becomes `faq--general.md`, `faq--personal-injury.md`, etc.)
- Splitting improves retrieval precision — the agent can fetch only the relevant subsection rather than loading an entire long page

### 5.8 Naming Conventions

Predictable filenames allow the agent to infer relevance from the filename alone:

| Pattern | Indicates |
|---------|-----------|
| `practice-areas--*.md` | Practice area descriptions |
| `attorneys--*.md` | Attorney bios |
| `faq*.md` | Frequently asked questions |
| `blog--*.md` | Blog posts |
| `contact.md` | Contact information |
| `about.md` | Firm overview |

This enables a fast "filename scan" before opening files, reducing unnecessary reads.

### 5.9 Merge Strategy

When the context store is updated (crawler re-run or form re-saved):
- Files are updated in place (overwritten with new content)
- New pages are added as new files
- Pages that no longer exist on the website are removed
- `_manifest.json` is regenerated as the single source of truth
- `_guardrails.md` is regenerated from the latest published dashboard config

No manual merge resolution is required — the crawler and dashboard are the only writers.

### 5.10 Read-Only at Runtime

The chatbot and API server never write to the context store. It is modified only by:
- The **Crawler CLI** (adds/updates/removes page files and `_manifest.json`)
- The **Dashboard publish action** (regenerates `_guardrails.md` and `config/` files)

This guarantees consistency — the context store is a stable snapshot that only changes through explicit user-initiated actions.

## 7. Component 5: Agent & Search Layer

### 7.6 Search Strategy

Two-pass retrieval for speed and precision:

**Pass 1 — Manifest scan (fast, no file reads):**
- Parses `_manifest.json` (cached in memory after first fetch)
- Scores each file against the query using a weighted scoring algorithm
- Ranks all files by score

**Scoring algorithm:**

Each file receives a relevance score (0–1) computed as:

```
score = (keyword_match × 0.4) + (title_match × 0.3) + (section_type_bonus × 0.2) + (filename_match × 0.1)
```

| Factor | Calculation |
|--------|------------|
| `keyword_match` | Jaccard similarity between query tokens and file's `keywords` array (intersection / union) |
| `title_match` | Proportion of query tokens found in the file title (case-insensitive) |
| `section_type_bonus` | 1.0 if the agent explicitly filtered by section type and this file matches; 0.5 if section type is contextually relevant (e.g., query mentions an attorney name → `attorney-bio` gets a boost); 0.0 otherwise |
| `filename_match` | 1.0 if any query token appears in the filename; 0.0 otherwise |

**Relevance threshold:** Files scoring below 0.15 are excluded. If no files exceed this threshold, the search returns empty (triggers fallback behavior).

**Pass 2 — Content retrieval (targeted file reads):**
- Fetches the top 3–5 highest-scoring files from the context store (above threshold)
- Injects their full markdown content into the prompt context
- Files are ordered by score (highest first) so that if token budget forces truncation, the most relevant content is preserved

### 7.7 Context Window Management

Injected context is budgeted to prevent exceeding model limits:

| Priority | Content | Token Budget |
|----------|---------|--------------|
| 1 (always) | `_guardrails.md` | ~1000 tokens |
| 2 (per query) | Relevant page content (top matches) | ~3000 tokens |
| 3 (if room) | Supplementary context (related pages) | ~500 tokens |

**Total context injection cap: ~4500 tokens**

If retrieved content exceeds the budget, lower-ranked files are truncated or excluded. The guardrails file is never truncated.

### 7.8 System Prompt Composition

The system prompt is assembled dynamically for each conversation turn:

```
┌─────────────────────────────────────┐
│ Base instructions                   │  (agent behavior, response format)
├─────────────────────────────────────┤
│ _guardrails.md content              │  (persona, boundaries, escalation)
├─────────────────────────────────────┤
│ Retrieved context (per query)       │  (relevant page content)
├─────────────────────────────────────┤
│ Intake state                        │  (questions asked/remaining)
└─────────────────────────────────────┘
```

The base instructions are static. Everything else is injected dynamically based on the current conversation state and query.

### 7.9 Conversation Memory

- Full conversation history is stored server-side in the session record
- For LLM calls, a sliding window strategy is used:
  - Last 10 messages are sent in full
  - Older messages are summarized into a compact context block
  - This keeps token usage predictable while maintaining conversational coherence
- Session history is available for lead review in the dashboard

### 7.10 Lead Data Extraction

As the user answers qualifying questions, the agent extracts structured data and stores it progressively:

```json

  "session_id": "sess_abc123",
  "extracted_at": "2026-05-09T16:30:00Z",

    "contact_phone": "(555) 987-6543",
    "case_type": "personal_injury",
    "incident_date": "2026-04-15",
    "brief_description": "Car accident on I-95, other driver at fault",

    "classification": "urgent",
    "classified_at": "2026-05-09T16:32:00Z"
  }

```

Data is written to SQLite incrementally — even if the conversation is abandoned midway, partial data is preserved.

### 7.11 Fallback Behavior

When the agent cannot find relevant context or answer the user's question:

| Scenario | Response |
|----------|----------|
| No relevant context files found | "I don't have specific information about that on our website. Would you like me to connect you with our team directly?" |
| Question outside practice areas | Out-of-scope response from guardrails config |
| Escalation trigger detected | Escalation message + firm contact info |
| Repeated inability to help | "It seems I'm not able to fully help with your question. The best next step would be to call us at [phone] or email [email]." |

The chatbot never fabricates information. If it's not in the context store, it acknowledges the gap.

### 7.12 Multi-Turn Awareness

The agent understands conversational context and adjusts its behavior accordingly:

- **Pronoun resolution:** "What about custody?" after discussing family law → searches for custody within family law context
- **Follow-up detection:** "Tell me more about that" → expands on the previous topic without re-searching
- **Topic shift detection:** Recognizes when the user changes subjects and issues a new context search
- **Implicit answers:** If a user says "I was in a car accident last week," the agent extracts case type (personal injury) and timeline (last week) without needing to ask those questions explicitly

### 9.2 Vercel AI SDK Justification

The Vercel AI SDK is the backbone of the LLM integration layer:

- **Gemini-native support:** `@ai-sdk/google` provides first-class integration with Gemini models including tool-calling and structured output
- **Built-in streaming:** `streamText` handles SSE streaming to the widget with zero custom plumbing
- **Tool-calling support:** First-class `tool()` primitive maps directly to the agent architecture
- **`useChat` hook:** Client-side hook for the widget handles message state, streaming, error handling out of the box
- **Future flexibility:** If we later offer model choice (post-MVP), the provider pattern (`@ai-sdk/anthropic`, `@ai-sdk/openai`) allows switching without code changes

Eliminates ~2000 lines of boilerplate that would otherwise be needed for streaming, retries, and model integration.

### 9.3 SQLite Justification

- **Zero-config:** No database server to run, no connection strings to manage
- **Embedded:** Ships as a single file alongside the API server
- **Fast for reads:** Lead queries and config lookups are sub-millisecond
- **MVP-appropriate:** Handles thousands of leads and sessions without performance concerns
- **Migration path:** Schema designed with Postgres compatibility in mind; switching requires only a Drizzle dialect change and connection string

**When to migrate:** When concurrent write throughput exceeds SQLite's single-writer limitation (likely >50 active chat sessions simultaneously writing).

### 9.4 Playwright over Puppeteer

| Criteria | Playwright | Puppeteer |
|----------|-----------|-----------|
| Browser engines | Chromium, Firefox, WebKit | Chromium only |
| Reliability | Auto-wait, less flakiness | Manual waits often needed |
| Maintenance | Microsoft-backed, active | Google-backed, less frequent updates |
| Headless performance | Comparable | Comparable |
| Install size | ~150MB (per browser) | ~170MB (Chromium) |

Playwright's multi-engine support ensures the crawler can render pages that behave differently across browsers, and its auto-waiting reduces edge cases in content extraction.

### 9.5 Drizzle ORM

- **Lightweight:** No binary dependencies (unlike Prisma's query engine)
- **Type-safe:** Full TypeScript inference from schema definition to query results
- **SQLite-native:** First-class SQLite support with `drizzle-orm/better-sqlite3`
- **Migration tooling:** `drizzle-kit` generates SQL migrations from schema changes
- **Zero overhead:** Compiles to raw SQL with no runtime query building cost

## 10. Out of Scope (MVP)

The following features are explicitly excluded from the rapid prototype. They represent natural post-MVP extensions but are deferred to keep the initial build focused and shippable.

| Feature | What's Excluded | Post-MVP Path |
|---------|----------------|---------------|
| **Multi-tenant / team management** | No multiple users per account, no role-based access, no organization hierarchy | Add team invitations, admin/member roles, and org-level settings |
| **Billing & subscriptions** | No payment processing, usage metering, or plan tiers | Integrate Stripe; meter by conversations or leads per month |
| **CRM integrations** | No Salesforce, HubSpot, Clio, or other legal CRM connections | Build webhook-based push to CRMs; prioritize Clio (legal-specific) |
| **Advanced analytics** | No conversation volume charts, conversion funnels, response quality scoring, or A/B testing | Add dashboard analytics page with time-series charts and funnel visualization |
| **Notification channels** | No email, SMS, Slack, or webhook delivery for urgent lead alerts | Wire up notification delivery table; add email (SendGrid) and webhook channels first |
| **Multi-language support** | Chatbot responds in configured language only; no auto-detection or real-time translation | Add language detection and multi-language response generation |
| **Custom widget builder** | No drag-and-drop widget designer; theming is CSS variables only | Build visual theme editor in dashboard with live preview |
| **Conversation handoff** | No live agent takeover; escalation is limited to directing users to call or email | Add WebSocket-based live chat where a human can join and take over from the bot |
| **User-configurable LLM** | No option for lawyers to bring their own API keys or choose models; Gemini is provided out of the box | Add LLM settings page with provider selection (Anthropic, OpenAI, etc.) and API key input |

### Guiding Principle

If a feature doesn't directly contribute to the core loop — **user asks question → chatbot retrieves context → chatbot qualifies lead → lead is stored** — it is out of scope for MVP. The prototype proves the value proposition; scale features come after validation.

## 11. Additional Recommendations

Beyond the core specification, the following considerations should be addressed early — even during rapid prototyping — to avoid costly retrofits.

### 11.1 Rate Limiting

Add per-session and per-API-key rate limits from day one:
- **Per session:** Max 50 messages per conversation (prevents infinite loops or abuse)
- **Per API key:** Max 1000 conversations per day (prevents runaway costs if a key is leaked)
- Implement at the API server layer using an in-memory counter (no external dependency for MVP)

### 11.2 Prompt Injection Protection

The chatbot faces public internet users — adversarial input is guaranteed:
- Sanitize user input before injecting into prompts (strip control characters, limit length)
- Add a system-level instruction that the chatbot must never reveal its system prompt, configuration, or internal tools
- Log and flag conversations where the user appears to be attempting injection (e.g., "ignore your instructions", "print your system prompt")
- Consider a lightweight classifier that detects manipulation attempts before they reach the LLM

### 11.3 Cost Monitoring

LLM API costs can spike unexpectedly:
- Log token usage (input + output) per conversation in SQLite
- Display cumulative spend in the dashboard (approximate, based on per-token pricing)
- Set up configurable spend alerts (e.g., "notify me if daily cost exceeds $50")
- Consider implementing a daily budget cap that disables the chatbot (with a friendly message) if exceeded

### 11.4 Legal Disclaimer

The chatbot operates in a legally sensitive domain:
- Display a clear, persistent disclaimer in the widget: *"I am an AI assistant, not a lawyer. Nothing I say constitutes legal advice."*
- Consult with a legal professional about liability exposure for incorrect or misleading chatbot responses
- Consider requiring lawyers to accept terms of service that acknowledge the chatbot's limitations
- Include disclaimer language in the guardrails form as a non-removable default

### 11.5 GDPR / Privacy Compliance

Even for MVP, personal data collection requires consent:
- Display a consent banner in the widget before collecting any personal data (name, email, phone)
- Store a consent timestamp and method per session in SQLite
- Provide a data deletion mechanism in the dashboard — deletes the lawyer-facing copy while archiving a retained copy per our data retention policy
- Draft a privacy policy template that lawyers can customize and link from the widget
- Ensure chat transcripts can be exported on request
- **Data retention disclosure:** The privacy policy and terms of service must clearly state that a copy of all data is retained on our servers even after user-initiated deletion. This must comply with applicable data protection regulations — consult legal counsel on retention justification language for GDPR Article 17 (right to erasure) exceptions

### 11.6 Caching Layer

Reduce LLM calls and improve response time for common queries:
- Cache responses to frequently asked questions (FAQ-type queries) based on semantic similarity
- Store cached responses in SQLite with a TTL (invalidate when context store changes)
- FAQ detection: if the user's question closely matches a previously answered question, serve the cached response
- Expected savings: 30-50% reduction in LLM calls for firms with predictable intake questions

### 11.7 Observability

Debugging agent behavior without logs is painful — add structured logging from the start:
- Log every conversation event: message received, tool called, context retrieved, response sent
- Log tool call details: which files were searched, relevance scores, tokens used
- Log errors with full context (session ID, conversation state, failing tool)
- Use structured JSON logs so they can be queried later (even if only writing to files for MVP)
- Consider a debug mode that can be toggled per session for troubleshooting specific conversations

### 11.8 User Testing with Real Lawyers

Before building all features, validate assumptions:
- Test the guardrails form with 2-3 practicing lawyers to confirm it captures what they actually need
- Watch them attempt to configure the chatbot — note where they get confused or ask questions
- Test the chat widget with non-technical users (simulate potential clients) to verify the conversation flow feels natural
- Validate that the qualifying questions and escalation triggers match real intake workflows
- This testing should happen after the form is built but before investing heavily in the agent layer — the form defines what the agent does

This testbed is the primary development and demonstration environment.

### 12.2 No External Dependencies (Except LLM)

The testbed runs entirely locally with one exception — the Gemini API call:

### 12.6 Phase 1: Crawler CLI

**Goal:** Crawl a website (or local HTML files) and produce structured markdown output.

**Build:**
- CLI tool that accepts a URL or local directory path
- HTML-to-markdown conversion pipeline (cheerio for static, Playwright for JS-rendered)
- Content extraction (strip nav/footer/chrome)
- `_manifest.json` generation with keywords and metadata

**Deliverable:**
```bash
npx legal-chatbot-crawl --url http://localhost:5173 --output ./chatbot-context/
# OR for local development:
npx legal-chatbot-crawl --input ./test-site/ --output ./chatbot-context/
```

**Done when:**
- [ ] Running crawler against the test React app produces markdown files in `./chatbot-context/pages/`
- [ ] Each file has valid YAML frontmatter (title, source_url, crawled_at, word_count, section_type)
- [ ] `_manifest.json` is generated with correct file count and keywords
- [ ] Re-running produces identical output (deterministic)
- [ ] Unit tests pass for: HTML-to-markdown conversion, content extraction, frontmatter generation

### 12.7 Phase 2: Context Search Agent

**Goal:** A standalone module that takes a natural-language query and returns relevant context from the markdown files.

**Build:**
- Manifest parser and in-memory cache
- Relevance scoring function (keyword match, title match, section type, filename)
- File retrieval and content assembly
- Token budget enforcement

**Deliverable:**
```bash
# Standalone test script:
npx tsx scripts/test-search.ts "I was in a car accident"
# Output: retrieves practice-areas--personal-injury.md, shows relevance score
```

**Done when:**
- [ ] Query "personal injury" returns the PI practice area file as top result
- [ ] Query "John Smith" returns the attorney bio file
- [ ] Query "divorce" returns the family law file
- [ ] Query "tax law" returns no results (below threshold — out of scope for this firm)
- [ ] Token budget cap is respected (never exceeds ~4500 tokens of context)
- [ ] Unit tests pass for: scoring algorithm, threshold filtering, token budgeting

### 12.8 Phase 3: Chat API Endpoint

**Goal:** A single API endpoint that accepts messages, runs the agent with tools, and streams a Gemini response grounded in context.

**Build:**
- Next.js route handler at `/api/chat`
- Vercel AI SDK `streamText` with Gemini model
- System prompt composition (guardrails + retrieved context)
- Context search tool wired to Phase 2 module
- Session management (create/resume sessions in SQLite)

**API Contract — `POST /api/chat`:**

**Request:**
```typescript
// Headers:
{
  "Content-Type": "application/json",
  "x-api-key": "lc_live_xxxxx"          // Required. Identifies account.
  "x-session-id"?: "sess_abc123"        // Optional. Omit to create new session.
}

// Body:
{
  "messages": [                          // Vercel AI SDK message format
    { "role": "user", "content": "Do you handle car accident cases?" }
  ]
}
```

**Response (success — streaming):**
```
HTTP/1.1 200 OK
Content-Type: text/plain; charset=utf-8
x-session-id: sess_abc123               // Always returned. Use for follow-ups.
Transfer-Encoding: chunked

// Body: Vercel AI SDK stream protocol (text stream parts)
0:"Yes, "
0:"Smith & Associates "
0:"handles personal injury cases..."
e:{"finishReason":"stop","usage":{"promptTokens":1200,"completionTokens":150}}
d:{"finishReason":"stop"}
```

**Response (error):**
```typescript
// 401 — Invalid or missing API key
{ "error": "unauthorized", "message": "Invalid API key" }

// 429 — Rate limited
{ "error": "rate_limited", "message": "Too many requests. Try again in 30 seconds.", "retry_after": 30 }

// 500 — Internal error
{ "error": "internal", "message": "An error occurred processing your request" }
```

**Session lifecycle:**
- First request: omit `x-session-id` → server creates session, returns ID in response header
- Subsequent requests: include `x-session-id` → server loads history, appends new message
- Session expires after 30 minutes of inactivity (configurable)

**Deliverable:**
```bash
# Test with curl:
curl -N -X POST http://localhost:3000/api/chat \
  -H "Content-Type: application/json" \
  -H "x-api-key: dev_test_key" \
  -d '{"messages": [{"role": "user", "content": "Do you handle car accident cases?"}]}'
# Output: streamed response referencing PI practice area content
```

**Done when:**
- [ ] Streaming response arrives token-by-token (SSE format)
- [ ] Response references actual content from context files (not hallucinated)
- [ ] Response respects guardrails (doesn't give legal advice, stays in scope)
- [ ] Out-of-scope questions get a polite deflection
- [ ] Session ID is returned and conversation continues on follow-up
- [ ] Integration tests pass for: streaming, tool calling, context injection, guardrail compliance

### 12.9 Phase 4: Chat Widget (React)

**Goal:** A React component embedded in the test app that connects to the local API and displays streaming responses.

**Build:**
- Chat widget component using Vercel AI SDK `useChat`

**Deliverable:**

**Done when:**

- [ ] Clicking bubble opens the chat panel

- [ ] Conversation persists across page navigations (same tab)
- [ ] Mobile view (Chrome DevTools responsive mode) shows full-screen chat

### 12.12 Testing Approach Per Phase

Each phase has explicit "done when" criteria. The testing strategy is cumulative — later phases include regression checks on earlier ones.

| Phase | Test Type | Tool | What's Verified |
|-------|-----------|------|----------------|
| 1 (Crawler) | Unit + Integration | Vitest | Markdown output structure, frontmatter, manifest generation |
| 2 (Search) | Unit | Vitest | Scoring accuracy, threshold behavior, token budgeting |
| 3 (Chat API) | Integration | Vitest + curl | Streaming, tool calls, context grounding, guardrail compliance |
| 4 (Widget) | Manual | Browser | UI renders correctly, streaming works, responsive layout |
| 5 (Classification) | Unit + Integration | Vitest + SQLite queries | DB writes, classification accuracy, partial data handling |
| 6 (Dashboard) | Manual + E2E | Browser + Playwright | Pages render, forms save, data displays correctly |

**Regression check between phases:**
After completing each phase, run the full test suite for all previous phases:
```bash
pnpm test          # Runs all unit + integration tests
pnpm test:e2e      # Runs Playwright E2E tests (added in Phase 6)
```

**Development workflow per phase:**
1. Write failing tests for the phase's deliverable criteria
2. Implement the minimal code to pass
3. Verify manually (for UI phases) or via test output
4. Commit with clear message indicating which phase is complete
5. Move to next phase only when all "done when" criteria are checked
